# Security fixes: finding → fix map

This file maps every finding of the adversarial security review of the fleet plan (ids S1-S21) and the measured `tailscale serve` facts to the place in this plan that fixes them: section, design paragraph and task ids (README 4.1). Every Critical, High and Medium finding is fixed. Low findings are fixed too; parts that are deliberately left out are listed under "Accepted risks" with the reason. The review text itself and the measurements name homelab hosts and live in the private part of the plan; the homelab-specific fixes (tailnet policy, firewall, users on the hub host, deploy procedure) are in the private hub-room runbook (§9) and are only referenced here.

Threat model used throughout: an agent on builder X has a shell as the laneboard user. Inside builder X, laneboard's guards are **cooperative** (README §2, §2 2.11, SECURITY.md via A10). The boundary that must hold is cross-machine: X → builder Y, X → hub, X → the user's devices.

## Accepted risks (with reason)

1. **Total control of the agent's own builder** (review residual 1, S7 remainder). Without separate uids for agents and laneboard, nothing laneboard does can stop an agent on X from killing, approving, unpausing, faking cost files or rewriting its local audit log on X. Remote-only rules close the local-API path; the rest is documented as cooperative (SECURITY.md, `docs/fleet/control.md`, inbox tooltip). Phase 2: a separate uid for laneboard on builders (then the preview/diff/transcript readers must open files with the agent's rights).
2. **Optional Bash sandbox for `default`-mode lanes and root-owned managed hook settings** (S7 part 3). The setting names are unverified on the installed Claude Code version; a wrong setting could silently block every lane. Kept as a documented HUMAN/phase-2 item (§8 §5, README HUMAN list).
3. **Ingress peer-uid check is opt-in** (S6 part c). It is implemented (A11) and fails closed, but defaults to off until the human has confirmed the uid `tailscaled` runs as on every box; until then a local process can still send serve-like headers to the ingress port, which only matters inside the cooperative model of item 1.
4. **No separate signer process on the hub** (S9 part b). It needs a second service, a socket protocol and its own audit; tonight's mitigations are the remote-only hub control, the separate feed user, the pinned deploy, `--ignore-scripts`, systemd sandboxing and the builder-side scopes and master switch. Phase 2.
5. **Trusted Types on the hub** (S10 optional part). The xterm DOM renderer has not been tested with `require-trusted-types-for 'script'`; turning it on blind could break terminals. Everything else in the hub CSP is enforced; the no-`innerHTML` lint covers `public/js/**`. HUMAN test later.
6. **Per-action restrictions per key** (the `actions?` list in the original S5 proposal). Three scopes cover the rollout phases; finer lists add config surface without a current need. Can be added later as an optional field.
7. **Hub compromise means every builder's secrets** (review residual 2). Bounded by branch protection and least-privilege push credentials on the forge side (human setup), manual key rotation (edit `hubKeys` on each builder).
8. **A compromised builder lies about its own state; kill does not contain; transcript/diff content passes through the hub's memory; budget pauses are advisory against an adversarial agent** (review residuals 3-6). Inherent to the design; the out-of-band runbook (§8) and fleet-kill results that list skipped builders by name are the answer.
