# Cockpit spec: decisions

Small, reversible choices made while writing the spec or building it. The owner may overrule any of
them; the overrule part says what changes then. Taste, one-way doors and anything security-relevant
go to `QUESTIONS.md` instead.

Format, one line each, numbered in order and never renumbered:

`D<n> <choice> — because <why> — overrule: <what changes if the owner disagrees>`

## List

- D1 In the spec "room" means the cockpit room; a Map node with `kind: room` is a "room node" — because laneboard already uses "room" for a Map node kind (`docs/map.md`) and the plan uses it for the agent's machine, so one word needs a qualifier — overrule: pick another name for the agent's machine (e.g. "cockpit host") and replace it across `spec/`; no code exists yet.
- D2 The Wall page has four layouts, `wall`, `canvas`, `split`, `switch`; the app's views get only the cockpit button, no canvas (pending Q-O22: with its recommendation b) this arrives with the Canvas slice, C1-C3 have `wall` only) — because the Wall is the screen's idle page and the plan keeps the app's views unchanged (Wall plan D1) — overrule: add a canvas to the app shell as well, `screens.md` §1 gains a row.
- D3 A screen's layout is stored on the screen (`localStorage` `cockpit.layout`), the URL `?layout=` wins over it (pending Q-O22: with its recommendation b) this arrives with the Canvas slice, C1-C3 have `wall` only) — because a kiosk sets its start URL once and a layout is about one display, not the room — overrule: store it in the room per device token (T3), so a reset browser keeps its layout.
- D4 Opening the pane, a running turn and an open microphone pause the Wall's 60 s idle timer; opening the pane stops the tour where the camera is — because the tour must not fly away from what the owner and the agent are talking about — overrule: let the tour run under the pane; `screens.md` §2 table changes.
- D5 The pane closes itself after 300 s without touch, never during a turn or with the microphone open (pending Q-O12: under its recommendation a) only the pane over the Wall and the app views closes; in `split`, `canvas` and `switch` the conversation is a column and never closes) — because an open pane over a touring Wall hides it from across the room — overrule: change the constant, or 0 for never.
- D6 The idle and layout numbers (60 s, 300 s, 1280 px, 608 px) are named constants in one client module — because research Q1 asks that thresholds live in one place for the owner to change — overrule: move them into config (`cockpit.*`).
- D7 (superseded by D116 under Q-O11's recommendation; holds if the owner picks Q-O11 b)) The cockpit button reads `AGENT`, 64x64 px, bottom right — because it names what the tap reaches, and "talk" is the talk button inside the pane (C2) — overrule: rename the label; one string in the client.
- D8 (superseded by D117 under Q-O12's recommendation; holds if the owner picks Q-O12 b)) In `split` the pane opens over the canvas half, never over the wall half (pending Q-O22: with its recommendation b) this arrives with the Canvas slice, C1-C3 have `wall` only) — because the agent's show commands move the wall's camera and the owner must see it — overrule: open it over the wall half; S-SCR-11 changes.
- D9 In `split` the canvas is a fixed 608 px column and the wall half takes the rest (pending Q-O13: written for a) until T130 specifies b)'s 96 px strip; pending Q-O22: with its recommendation b) this arrives with the Canvas slice, C1-C3 have `wall` only) — because the card grid (T11) then has one size on every split screen — overrule: a 50/50 split; T11's grid scales with it.
- D10 A lost room link shows on screen only after a 5 s grace; the room sends a heartbeat every 10 s and the link counts as lost after 25 s without a frame — because short blips should not flash a warning across a desk screen (written back by the final round: round 18 cited D10-D17 in `screens.md` §6-7 but its decision lines were lost) — overrule: change the three constants; S-SCR-17/18 change.
- D11 The room link retries with the board socket's backoff, exactly as `createSource` in `public/js/core/net.js` does (delay starts at 500 ms and is multiplied by 1.8 before each try, cap 15 s, reset on open: tries 0.9, 2.52, 5.436, 10.68, 20.13, 35.13 s after the loss, then every 15 s; `screens.md` §7.1, corrected by T28; its own loop on the same constants, D263) — because one retry rule is easier to reason about and test — overrule: give the room its own backoff constants.
- D12 A draft typed while the room is down is never sent on its own when the room comes back — because a stale instruction sent minutes later can do the wrong thing — overrule: send it on reconnect; S-SCR-19 changes.
- D13 Pairing codes are 6 characters from `23456789ABCDEFGHJKMNPQRSTUVWXYZ`, valid 300 s, at most 10 open per room (the 11th request gets 429, retry after 30 s) — because short enough to read across a desk and too many to guess within 300 s under the cap (pending Q-O10: the code and D162's `pairSecret` are part of how a screen is approved, so they stay with that question, not with D90; T61, `reviews/40-security.md` contradictions list) — overrule: change length, lifetime or cap; S-SCR-15 changes.
- D14 A screen keeps the conversation and the cards in memory only, never in browser storage — because a screen should hold nothing worth stealing (plan §2) (security-adjacent, confirmed by D90; T17 decides where the device token itself lives) — overrule: cache them in storage so a reload while the room is down still shows them.
- D15 With the board down, the tour keeps flying over the grey snapshot without "flies to trouble" — because a grey map has no trouble to rank, and a moving Wall shows the screen is alive — overrule: stop the tour while the board is down; S-SCR-21 changes.
- D16 A board that never loaded shows `Waiting for the board at <origin>…`, a retry countdown and `SHOW DEMO` (reloads with `?demo=1`) — because never an empty screen (`docs/plans/product.md`) — overrule: drop the demo button; S-SCR-22 changes.
- D17 The cockpit is configured only when the process that serves the page has a `cockpit` section, either with `cockpit.agent` (it is the room itself) or with `cockpit.forwarded: true` (its front forwards `/api/cockpit/` to a room, D129); otherwise it is unconfigured: no cockpit button, no canvas half, the board as today (`hello.cockpit:false`, D93; was "without `cockpit.url`", replaced by T86); except `?demo=1` with no cockpit, which draws the cockpit on the demo link (D148, `c1-talk.md` §15) — because a stranger without a room must see a normal laneboard (product rule: never tied to one) — overrule: show the button with a "not set up" pane instead.
- D18 The cockpit pane is 608 px wide on the right, full height on the Wall page, between the header and the tape in the app (`z-index` 35), the same width as the canvas column — because one width means a reply wraps alike in the pane and in the canvas column, and the left 759 px of the Wall stay in sight as in `split`; on a viewport under 900 px wide the pane is the full width instead (D249, T77) — overrule: change the one constant; `c1-talk.md` §1 and S-C1-01/03 change.
- D19 A tap on the view behind the open pane acts on the view and does not close the pane; no swipe-to-close in v1 — because the owner points at the Map while the agent talks, and a swipe on a slanted desk screen fires by accident — overrule: close on an outside tap; S-C1-02 changes.
- D20 Opening the pane focuses the input only with a fine pointer; on a touch screen the on-screen keyboard comes with a tap in the input — because the keyboard would cover half the pane on every open, and voice is the main path — overrule: always focus.
- D21 Pane type: prompt, reply, input and live words mono 28 px (line height 1.4; `TYPE_TALK`, pending Q-O18, T97), code, tables and tool lines 18 px, labels and buttons 16 px caps; the floor (T43, review 31 finding 4): no text under 16 px, no instruction under 18 px (the line slot's messages, the status line, the header's turn state; D167), checked by S-C1-40; named constants in D6's module; replies use the mono face (the app vendors only mono and the condensed label face) — because research Q1 puts the floor near 22 px at 60 cm and 26-30 px for text read while speaking, and 28 px still gives 33 characters per line in 560 px and 21 in the input (pending Q-O9: the panel's real size) — overrule: change the constants (22 px: 42 and 27 characters, input 157 px at 4 lines), or vendor a proportional face for prose.
- D22 Replies are a Markdown subset: raw HTML shows as literal text, images as `[image: alt]` with nothing fetched, links show their text and host and are not tappable (security-adjacent, confirmed by D90; T17 lists it) — because a kiosk that follows a link leaves the board, and a reply can carry text from logs or web pages — overrule: links open in a new tab; S-C1-09 changes.
- D23 Code blocks never wrap and scroll sideways, 12 lines then `SHOW ALL <n> LINES`; tables scroll sideways with the first column fixed and draw every row (T50, review 36 finding 8) — because log lines and wide tables lose their shape when wrapped, one long log block must not push the answer out of sight, and 20 table rows are one flick — overrule: wrap code lines; change the 12-line limit; fold tables again.
- D24 Tool-line words come from one client table keyed by tool name (`one` / `many`, one `{target}` field), consecutive calls of one tool fold into one line, failures are grey words (` · 1 failed`), unknown tools read `used <name>` — because the plan wants "read 3 feeds", not raw calls, and an agent other than Claude Code still gets a readable line — overrule: edit the table; S-C1-06/07 change.
- D25 In a reply only the four marks `■ ▲ ● ○` are coloured, the rest is grey — because the colour rule says hue only travels with its shape, and the agent must not be able to paint a word red — overrule: let the agent colour status words too.
- D26 The conversation follows a growing reply while its end is within 48 px of the bottom; scrolled up, it stays put and `↓ NEW` jumps back instantly — because reading an earlier line while the agent writes must not be yanked away — overrule: change the 48 px, or always follow.
- D27 The pane draws the last 50 turns, `SHOW EARLIER` adds 50 at a time — because a day-long conversation must not slow the pane on a tablet — overrule: change the 50.
- D28 Every speed budget `B<n>` (`README.md`) is measured by the screen itself as `performance.mark('cockpit:B<n>:start|end')` plus one `performance.measure('cockpit:B<n>')`, read by tests and, on the real screen, in remote devtools; no `?perf=1`, nothing drawn, no console line (T33; `?perf=1` dropped by T53/T35); stand-in runs that miss a row fail, and only the owner widens a row — because one measurement serves the tests and the owner's real tablet alike, a kiosk has no console to read, and a loop must not loosen its own budget to pass — overrule: drop the marks and time from outside in Playwright only; or bring back `?perf=1` as one `console.info('cockpit:B<n>', ms)` per measure.
- D29 Listening starts on `pointerdown` of the talk button for both tap-tap and hold-release; the hold threshold is read only at `pointerup` to decide send (hold) or keep listening (tap) — because B1 (≤ 0.2 s) cannot wait for a 400 ms threshold, and starting to listen is undone by cancel while sending only happens on release (WCAG 2.5.2, research Q1); a brushed button therefore listens until cancelled or sent, T6 specs that cancel — overrule: start listening only after the threshold or on release of a tap; B1 then becomes ≤ 0.6 s.
- D30 The input is a textarea that grows to 4 lines (182 px at 28 px, D21) then scrolls; `Enter` sends and `Shift+Enter` breaks the line on every keyboard; a prompt is at most 8 000 characters, longer text stays in the input with `SEND` disabled — because the owner's habit is the terminal's Enter, and a cut-short paste would send something the owner did not write — overrule: `Enter` breaks the line on the on-screen keyboard; change the 4 lines or 8 000.
- D31 A sent prompt is drawn at once with `· SENDING` until the room confirms; no confirmation in 5 s shows `NOT SENT` with `RETRY`/`EDIT`, never a resend on its own — because B8 needs the block at once, and a silent resend could run an instruction twice — overrule: retry automatically once; S-C1-18 changes.
- D32 During a turn the `SEND` slot reads `STOP` while the input is empty and `SEND` (which steers: the words join the running turn, `c1-talk.md` §8) while it holds text; `STOP` interrupts with `cancelQueued`, and a stop not ended by the agent in 5 s is forced by the room; its guard and look are D268 (pending Q-O1) — because one place for both keeps the input row as it is, research Q8 says a mid-turn message is read at the next tool boundary, and research Q2 offers no guaranteed interrupt — overrule: a separate `STOP` in the header, so "stop, do this instead" works with a draft in the input; change the 5 s.
- D33 A stopped turn keeps its text as at the tap, gets `STOPPED AT HH:MM`, and nothing it sends later is drawn (the room's log keeps it) — because text changing after the owner said stop reads as the agent ignoring them — overrule: draw the turn's late events too.
- D34 Turn errors are grey lines with a fixed message per code (E1-E8, E6 retired by D57), shown on every screen; `RETRY`, `EDIT`, `GO ON` act only on a tap — because an agent failure is not fleet trouble (the colour rule), and D12's "never sent on its own" holds for every resend — overrule: retry `model-failed` automatically once.
- D35 A turn's age shows in its label from 3 s on (D235; was 10 s); a long reply is drawn whole, with no `↑ TOP OF ANSWER` and no `SHOW THE REST` (T50, review 36 finding 8) — because a long silence must not look like a hang, a flick goes back to the top, and the bridge already asks the agent to lead with the answer — overrule: bring back the 20 000-character fold or the top button; S-C1-21 changes.
- D36 `NEW` asks in a bar (`START` / `KEEP`, gone after 10 s), then the room starts a new session at once, with no handover note and no extra turn state; the old turns stay above a `NEW CONVERSATION · HH:MM` divider (T51, pending Q-O2 d) — because a new conversation is one tap away from losing the thread, and the plan's fresh start reads only the written context a laptop session would — overrule: start without asking, or (Q-O2 c) ask the old session for a note first; S-C1-22 changes.
- D37 Drafts, live partial words, pane state, scroll, opened rows and the `NEW` bar are per screen; prompt labels carry no screen name in C1 (T51) — because one conversation is shared (plan §2) but a half-typed thought is not, and the owner has not said they use two screens (Q-O9) — overrule: mirror live partials to every screen, or name the sending screen once several screens pair (Q-O21).
- D38 The `NEW` header button is 72 px wide (the others 96 px); `RAW` is gone with the raw view (T50) — because with `CLOSE` and `SCREEN` it must fit the 608 px header beside `COCKPIT` and the turn state — overrule: move `NEW` elsewhere; `c1-talk.md` §1 changes.
- D39 The hold threshold is 400 ms, read at the first `pointerup`: shorter is a tap (listening goes on, the next tap's release sends), longer is a hold (the release sends); a named constant in D6's module — because 400 ms is Android's long-press default (research Q1) and D29 already starts listening on `pointerdown` — overrule: change the constant; S-C2-02's timings move with it.
- D40 A hold sends only when released in the send zone, x ≥ 1232 and y ≥ 776 to the screen's right and bottom edges, outside the `SEND` slot padded 8 px (x 1192-1272, y 816-896); a release elsewhere (slide off to the left or up, or onto the slot) or a `pointercancel` does not send: the microphone closes, the words stay as an editable draft, hint `MICROPHONE OFF · TEXT KEPT`, which after a `pointercancel` or a release on the slot stays until the next touch (D168) (`c2-voice.md` §2, T42/T95, pending Q-O19) — because WCAG 2.5.2 wants a way to abort a release, a thumb drifting off the glass at the bottom-right still means "send" (review 31-touch.md finding 10), a lift where the eye sees the slot does not, and a draft loses nothing the owner said (review 63-touch.md findings 2, 12) — overrule: send on any release, or send on `pointercancel` too; S-C2-07 changes.
- D41 After the release the screen waits at most 3 s for the speech service's final text, then keeps the last words shown as a draft, not sent — because sending a guess the service never confirmed could run the wrong instruction, as D12 — overrule: send the last partial after the wait; change the 3 s.
- D42 While the microphone is open the `SEND` slot is blank, `inert` and `aria-hidden` (`data-send="none"`), and `CANCEL` is a 64x64 `✕` named `Cancel` (`[data-talk-cancel]`, 28 px, no word: 16 px `CANCEL` does not fit 64 px, D167) at the row's left end, x 784-848, in the language button's rect; it closes the microphone, drops the spoken words, keeps a typed draft, sends nothing, and for 5.0 s the same rect holds `UNDO` with the hint `WORDS DROPPED` (`c2-voice.md` §3, T42/T95, pending Q-O19 a, d) — because the finger that sends by habit lands on the slot, so nothing there may drop dictation, and a drop by mistake must be undoable (review 31-touch.md finding 3, 63-touch.md finding 2); 64x64 in the language button's place instead of review 63's 48x48 inside the live-words box, because that button has no job while the microphone is open, so the default row (DE/EN, T107) does not move, and the live words keep their width — overrule: the old layout (`✕` in the `SEND` slot, no undo), or the 48x48 inside the live words; S-C2-01, S-C2-04, S-C2-07, S-C2-10 change.
- D43 While the microphone is open the textarea is swapped for a read-only `[data-talk-text]` with a firm and a tail span in the same rectangle and type — because a textarea cannot colour the part of its text that may still change — overrule: show the words in the textarea, all one colour; S-C2-03's colour check goes.
- D44 Words spoken into an input that holds a typed draft follow the draft after one space; `CANCEL` removes only the spoken part — because the owner may type a name and speak the rest — overrule: speaking replaces the draft.
- D45 Listening ends on its own after 30 s with no word (nothing sent) or 120 s in all (words kept as a draft, not sent); every close without a send shows one hint, `MICROPHONE OFF`, plus ` · TEXT KEPT` when spoken words are in the input, for 5 s (after a limit until the next touch, D168) (T49, review 36 finding 13) — because a brushed button (D29) must not leave a microphone open on a desk, auto-sending a long speech could send a half thought, and three wordings for one event is two too many — overrule: change the 30 s / 120 s, or send at 120 s; name the cause in the hint.
- D46 The screen opens the microphone on each press and stops every track when listening ends; no stream lives between presses; audio from before the room's audio channel is open is held and sent first — because the browser's microphone indicator should be on only while the button shows it (safe by default), and holding early audio keeps the first word — overrule: keep the stream open for N s after a turn for a faster second press.
- D47 A tap on the live words during a tap-gesture listen stops listening and puts the final into the textarea, focused, caret at the end, nothing sent; during a hold or in `final` it is ignored; no word is selected (T49, review 36 finding 5) — because the plan's "a tap on the text lets the owner fix a word" needs the keyboard up, and mapping the tapped word onto a final that differs in case, punctuation and word count selects the wrong word often enough to be worse than nothing — overrule: select the tapped word, or make the text editable while listening; S-C2-11/12 change.
- D48 `cockpit.stt.language` is a code, `auto` or a list, default `["en", "de"]` so the button shows out of the box (`spec-input.md` §4: "a DE/EN choice in the UI"; a one-language user sets one code, T107); a list draws a 64x64 language button at the input row's left end that cycles the codes, the first is the default, the choice is per screen in `localStorage` `cockpit.lang`, fixed for the duration of a press — because `spec-input.md` §4 wants a DE/EN choice in the UI, one tap is the cheapest switch, and changing language mid-utterance would mean a new speech session — overrule: put the choice in the `SCREEN` sheet, or make it room-wide; S-C2-13 changes.
- D49 `cockpit.stt.url` defaults to `none` (no talk button, `SEND` in its place, placeholder `Type a message`); `ws://` only on loopback; the service's token comes from `cockpit.stt.tokenFile` and goes in the `Authorization` header, never the query; no `context` word list in v1 (security-adjacent, confirmed by D90; T17 lists it) — because plan §5 wants `none` as the default, research Q4 says query strings end up in logs, and a context the backend refuses closes the session — overrule: add `cockpit.stt.context`; draw a disabled talk button under `none`.
- D50 Speech service failures are two causes: `stt-down` when no word had been shown (no `config` message 2.0 s after the press, 401, 403, an error update, a bad close, or no final 3.0 s after the release), with `data-talk-detail` `no-answer|busy|token|failed` named in the line; `stt-failed` when words had been shown (they go into the textarea, not sent); no slow hint, no cross-screen mark (T49, review 36 finding 6) — because for the owner the cases are "nothing was heard" and "words heard, not finished", the detail keeps the setup hint, and lagging words show themselves — overrule: bring back the slow hint (no message 4.0 s, lag ≥ 2.0 s) or separate codes per cause; S-C2-15..17 change.
- D51 The talk key is `F13` (overruled per screen with `?talkKey=`), `keydown` is the press and `keyup` the release, repeats ignored, active whatever has the focus — because macro keys can send F13-F24 and no app or text field uses them — overrule: change the default key, or put it in config; S-C2-20 changes.
- D52 (C2b, `c2-voice.md` §14) The button API answers after the target screen reports its new state, at most 1.0 s (504 after), allows 5 calls per second per token, refuses any request with an `Origin` or `Cookie`, and audits every call — because a home automation button wants to know whether it worked, and a page in a browser must never be able to press talk — overrule: answer 202 at once without waiting; change the rate.
- D53 (superseded by D120: no ring at all) With the talk button bottom right (Q-O11 recommendation), the room-down ring sits on the talk button, not on `CHAT` — because the talk button is the one that stops working when the room is down, and `CHAT` still opens the pane with the status line and the readable conversation — overrule: ring on `CHAT` too, or on `CHAT` only under Q-O11 b); `screens.md` §7 and S-SCR-17 change.
- D54 The pane's status line (`screens.md` §7) and the canvas's room-down strip (`c4-show-canvas.md` §7.6) are 80 px tall (two lines of 18 px), not 48 px — because their exact texts (64 and 66 characters of 18 px mono, ~11 px each) do not fit one line beside `RETRY NOW` or across 576 px; shortening the texts would drop "since when" or "retrying" — overrule: shorten the texts to one line (`Room down since 06:41 · retry 12 s`) and keep 48 px; `screens.md` §7 and `c1-talk.md` §1 change.
- D55 The physical button's HTTP API (button tokens, `POST /api/cockpit/talk`, the CLI, S-C2B-01/02, D52) is a later slice C2b, not C2; C2 ships the talk key only, and the two moved scenarios get new ids `S-C2B-01/02` (old ids S-C2-18/19 retired, never reused) — because `spec-input.md` §4 says "Later, a physical button", the talk key already serves a USB macro key, and a new authenticated door that opens a desk microphone should not come before the owner has used voice once (review 36-skeptic.md finding 2) — overrule: move §14 back into C2's build night, and Q-O8/Q-O20 back above "Can wait".
- D56 The header's turn state draws `READY`, `● WORKING` or `● STOPPING`; `data-turn` keeps `idle`, `thinking`, `working`, `answering`, `stopping` for tests (T50, review 36 finding 9) — because the prompt's `· SENDING`, a tool line's `●` and the `▍` cursor already show which of the three is happening, and the header is the farthest text from the hand — overrule: draw `● THINKING` / `● ANSWERING` again; S-C1-04/16 and S-C2-09 change.
- D57 A turn that ends with a model-service error is E8 `failed`, `The answer failed: {detail}.` with the service's message as `{detail}`; E6 `model-failed` is retired, never reused (T50, review 36 finding 13) — because the two lines differed by four words and had the same button — overrule: bring back E6 with `the model service said`; S-C1-20 changes.
- D58 The MCP server's key is `laneboard` (tools `mcp__laneboard__<tool>`), served by the room process as Streamable HTTP at `/mcp` on `127.0.0.1:7790` (`cockpit.mcp.port`) with a bearer token written fresh to `<stateDir>/cockpit/mcp.token` (0600) at each start, requests with an `Origin` refused (security-adjacent: T17 lists it) — because `c1-talk.md` §5 already matches `mcp__laneboard__`, and one process holding the screens' connections and the tools lets `focus` (T9) and the show commands (C4) share state without a second channel (research Q5) — overrule: a stdio server (`laneboard mcp`) spawned by the agent that calls the room back over loopback; `c3-see.md` §1 changes, the tools do not.
- D59 MCP results give times as ISO 8601 in the board's timezone with its offset and durations as whole seconds or minutes named in the field (`ageS`, `waitMin`), never epoch numbers — because the agent answers the owner in local clock time and converting epoch ms is where a model slips by an hour — overrule: epoch ms plus a `tz` field; every example in `c3-see.md` §4 changes.
- D60 Each read-tool result is at most 24 000 characters of JSON with a cap per list and a `truncated` count; at most 4 calls at once and 60 per minute per agent session — because Claude Code saves results over 25 000 tokens to a file instead (research Q5), a quarter of that leaves room for several calls in one turn, and a looping agent must not hammer the hub — overrule: change the limits; S-C3-06 changes.
- D61 A screen sends `focus` on a route, selection, wall-state or pane change and when the camera rests 300 ms with a new `inSight`, at most once per 500 ms (merged), and attaches its focus to every prompt; the room keeps the latest and the at-prompt focus per screen in memory only (T9, `c3-see.md` §8.1) — because "what's wrong here?" must mean what was on screen at the send, research Q5 found no way to push state to the model so the agent pulls it, and where the owner looks is nobody's log — overrule: send only with prompts (no live `focus`), or keep focus in the conversation log; S-C3-12/15 change.
- D62 "Ask about this" works on Map and Wall nodes only in C3; Board cards, Runs rows and other views do not get it — because the plan says "any node" and those are the views with nodes, and the chip then always names a Map node `focus` can resolve — overrule: add it to Board cards and Runs rows (the chip then carries a lane fkey or a run id).
- D63 The hold menu rides on the Map's existing 500 ms long press (`LONG_PRESS_MS`, `interact.js`), which still selects the node and opens the inspector; a mouse right click opens the same menu; without a configured and paired cockpit the hold is unchanged and no menu exists — because one hold with two meanings on one page would make the owner guess, and a board without a room must stay as it is (product: never tied to one) — overrule: a separate hold time for the menu, or the menu instead of the inspector.
- D64 `ASK ABOUT THIS` opens the pane with the chip and nothing else: no microphone, no keyboard — because the microphone opens only on a press of the talk button (D46, safe by default) and D20 keeps the keyboard down on touch — overrule: start listening at once (one press fewer; S-C3-10 then expects a `getUserMedia` call).
- D65 One context chip at a time; it travels with the next prompt only and then shows in that prompt's label as `ABOUT <label>` — because two chips would need an order and a rule for which one "this" means, and a chip that stayed on would silently colour every later question — overrule: a sticky chip until removed, or several chips.
